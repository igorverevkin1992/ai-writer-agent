## Роли системы (зафиксированы, не пересматривать)

1. **Компилятор** — детерминированный код (НЕ LLM): собирает окно контекста главы из библиотеки по номеру главы.
2. **Писатель** — Gemini 3.1 Pro через API: генерация прозы по окну; версия модели пиннится в конфиге; температура фиксирована; никакой памяти между главами.
3. **Верификатор-1** — Python-скрипты: метрики фразы, стоп-листы, поиск вставок текста промпта в прозу, межглавные повторы (n-граммы от 5 слов против корпуса принятых глав), счётчик наречий-усилителей, плотность «был», объём, TTR.
4. **Верификатор-2** — Claude через API: смысловые проверки по чек-листам 4.1–4.3 (фокализация, эпистемика по матрице, информационный режим, самовольные факты с классификацией «вычеркнуть/канонизировать»).
5. **Канонист** — Claude через API + подтверждение автора: после приёмки главы формирует записи в реестры, снапшоты, коммит.
6. **Шоураннер** — человек: приёмка, правки, канонические решения. Ни одна запись в канон не проходит без его подтверждения.

## Что должно войти в ТЗ (обязательная структура документа)

1. **Цели и рамки.** Что система делает и чего принципиально не делает (не принимает канонических решений; не публикует; не редактирует канон без человека).
2. **Глоссарий** (канон, окно контекста, такт, флаг, самоволка, золотой тест, снапшот и т.д. — термины брать из библиотеки).
3. **Пользователи и сценарии.** Один пользователь-шоураннер; сценарии: производство главы (такт из 9 шагов по архитектуре), правка канона, пере-тест моделей, откат.
4. **Архитектура и модули.** Диаграмма компонентов; для каждого модуля: назначение, входы/выходы, интерфейс (CLI-команды и/или функции), зависимости.
5. **Модель данных.** (а) Канон: MD-файлы в git как источник истины; (б) машиночитаемые выгрузки: JSON-схемы для стоп-листов, эпистемической матрицы (персонаж × факт × глава × источник), реестра закладок, корпуса принятых глав; правила генерации выгрузок из MD и валидации; (в) хранение правок автора (текст-до/текст-после/глава/классификация); (г) состояния главы — конечный автомат: собрано → сгенерировано → верифицировано-1 → верифицировано-2 → на приёмке → правки → дифф-контроль → принято → зафиксировано; допустимые переходы и откаты.
6. **Интеграции.** Gemini API и Anthropic API: аутентификация из конфига/переменных окружения, пиннинг версий моделей, фиксированные параметры генерации, ретраи и таймауты, обработка отказов, учёт стоимости по токенам в лог. Требование приватности: только API-каналы с политикой необучения на пользовательских данных; ключи не хранятся в репозитории.
7. **Функциональные требования по модулям** — детально, с нумерацией (FR-1, FR-2 …), включая как минимум:
   - Компилятор: правила отбора контента в окно (какие разделы каких файлов, фильтрация матрицы по участникам сцены, запреты информрежима главы, закладки главы); шаблон окна = формат `ПРОМПТ_Глава5.md` v1.1; детерминированность (одинаковый вход → одинаковое окно).
   - Верификатор-1: полный список проверок с числовыми порогами (взять из `02` с учётом Р-015 и Р-016: средняя фраза 9–12, средняя <7 — брак, короткие 30–45%, длинные ≥25 слов ≤5%, «был» ≤1/250 слов, усилители ≤2/1000, объём по брифу, substring-поиск окна в тексте, n-граммы ≥5 слов против корпуса); формат вердикта ПРОШЛО/ФЛАГ с цитатой и правилом-источником.
   - Верификатор-2: промпт-шаблоны для чек-листов 4.1–4.3; вход = текст + релевантные выгрузки; выход = структурированный список флагов (тип, цитата, нарушенное правило, рекомендация); отдельный список «самоволок» с кнопочным решением автора «вычеркнуть/канонизировать».
   - Цикл правок: передача правок Писателю с инструкцией «внести точно, не меняя ничего сверх»; дифф-контроль внесения (Верификатор-1): доля внесённых, список самовольных изменений.
   - Канонист: генерация предложений записей в реестры (3.1/3.2/3.3/1.2) и правил вкуса (6.1/6.2) из принятых правок; пакетное подтверждение автором; git-коммит как атомарная фиксация приёмки.
   - Регрессионный корпус: хранение «золотых тестов» (фрагмент + ожидаемые флаги); команда прогона Верификаторов по корпусу с отчётом «поймано/пропущено»; блокировка релиза конфигурации при пропуске.
   - Дашборд метрик: правки/1000 слов по главам, дрейф метрик Э1 по главам (флаг при отклонении >20% от среднего части), TTR нарастающим окном, расход токенов.
8. **Нефункциональные требования.** Локальный запуск на машине автора (macOS/Windows); CLI-first (этапы 1–2), веб-интерфейс — этап 3; русский язык интерфейса и сообщений; полная работоспособность деградированного ручного режима при отказе любого компонента; бэкап репозитория; журналирование каждого вызова API (промпт, ответ, модель, версия, токены) в локальный лог.
9. **Этапность** — строго по дорожной карте архитектуры: Этап 1 (репозиторий, выгрузки, Компилятор, счётчики Э1, обвязка API), Этап 2 (пайплайн такта, правки, регрессия, дашборд-страница), Этап 3 (React-панель шоураннера). Для каждого этапа — состав, критерии приёмки, оценка трудоёмкости.
10. **Тестирование.** Юнит-тесты счётчиков на эталонных текстах из библиотеки (глава 4 v2 — «зелёный» образец; тексты отборочного теста — «красные» образцы с известными нарушениями); регрессионный корпус; ручной сценарий сквозного такта.
11. **Риски и открытые вопросы.** Отдельным реестром: смена версий моделей, доступность API по региону, размер окна контекста при росте библиотеки, конфликт правок канона.
12. **Критерии приёмки системы в целом.** Сквозной такт главы проходит за ≤40 минут работы автора; все проверки Р-016 автоматизированы; ни один путь записи в канон не обходит подтверждение автора.
