## 1. Цели и рамки

**1.1. Цель.** Система автоматизирует производственный такт главы книжной серии «УГАР»: сборку окна контекста из библиотеки канона, генерацию прозы LLM-Писателем, двухэшелонную верификацию, цикл авторских правок и фиксацию принятого в реестры канона — при сохранении за автором всех канонических и вкусовых решений.

**1.2. Система ДЕЛАЕТ:** детерминированно собирает окна контекста; вызывает API Писателя и Верификатора-2; исполняет формальные проверки; ведёт состояния глав; управляет циклом правок с дифф-контролем; готовит пакеты записей в канон на подпись автору; ведёт регрессионный корпус, метрики, журналы и git-историю.

**1.3. Система принципиально НЕ ДЕЛАЕТ:** не принимает канонических и вкусовых решений; не записывает в канон без явного подтверждения автора; не публикует и не экспортирует рукопись вовне; не редактирует библиотеку канона по собственной инициативе любого LLM-компонента; не имеет облачного бэкенда — весь контур локален, наружу выходят только вызовы API моделей.

**1.4. Источник истины.** Папка `УГАР_Библиотека/` (Markdown, git). Настоящее ТЗ реализует документ `ИНСТРУМЕНТ_Архитектура_конвейера.md` без пересмотра; при расхождении ТЗ и архитектуры приоритет у архитектуры, расхождение оформляется правкой ТЗ.

## 2. Глоссарий

- **Канон** — совокупность документов `УГАР_Библиотека/`; единственный источник истины (Конституция 0.1).
- **Окно контекста** — самодостаточный промпт главы для Писателя, формат `Тест_Писателя/ПРОМПТ_Глава5.md` (v1.1).
- **Такт** — жизненный цикл одной главы, 9 шагов (Архитектура §4).
- **Флаг** — зафиксированное проверкой отклонение: `{тип, цитата, правило-источник, рекомендация}`.
- **Самоволка** — факт/мотивировка/деталь в тексте Писателя, отсутствующая в брифе и каноне; требует решения автора: «вычеркнуть» или «канонизировать».
- **Золотой тест** — фрагмент текста с заранее известным набором ожидаемых флагов; элемент регрессионного корпуса.
- **Снапшот** — зафиксированный срез состояния мира/знаний на конец тома (реестр 3.5).
- **Э1 / Э2** — эшелоны верификации: скрипты / LLM-Верификатор.
- **Приёмка** — явное подтверждение автора, после которого глава считается принятой и фиксируется атомарным git-коммитом.
- **Выгрузка** — машиночитаемое (JSON) представление части канона, генерируемое из MD.

## 3. Пользователи и сценарии

**3.1. Пользователь.** Один — автор-шоураннер. Многопользовательский режим не требуется; блокировки не проектируются (Допущение Д-5).

**3.2. Сценарий А «Такт главы»** (основной): `export → compile N → write N → verify1 N (авто-повтор при браке, ≤2) → verify2 N → review N (автор: правки + решения по самоволкам) → apply-edits N → diff-check N → accept N → canonize N`. Подробно — раздел 7.

**3.3. Сценарий Б «Правка канона».** Автор правит MD-файлы библиотеки руками или через Канониста; система валидирует структуру (Д-1), перегенерирует выгрузки, коммитит с осмысленным сообщением; изменение норм — только при наличии записи в `36_Журнал` (проверка ссылки Р-№ в сообщении коммита — предупреждение, не блокировка).

**3.4. Сценарий В «Пере-тест моделей».** По команде `retest` система собирает пакет раунда 1 протокола отбора (`Тест_Писателя/ПРОТОКОЛ_ОТБОРА.md`) на свежем брифе; прогон по сторонним моделям — полуручной (Д-10); результаты и решение — записью в журнал 3.6.

**3.5. Сценарий Г «Откат».** Любая глава возвращается в предыдущее состояние командой `rollback N --to <состояние>`; принятые главы откатываются только git-revert'ом соответствующего коммита с автоматическим пересчётом выгрузок и корпуса.

## 4. Архитектура и модули

**4.0. Технологический стек (предложение).** Python 3.11+ (пайплайн, счётчики, CLI на `typer`), `pydantic` — схемы данных и валидация выгрузок, официальные SDK `google-genai` и `anthropic` — интеграции, `pytest` — тесты, git (через `subprocess`) — версионирование канона, `Jinja2` — шаблон окна, статический HTML+`plotly` — дашборд этапа 2, React — только этап 3. Обоснование: чистый Python без БД и серверов покрывает все требования, минимизирует поверхность отказов, полностью работает локально и деградирует в ручной режим на любом шаге; Markdown+git остаются человекочитаемым источником истины, что прямо требуется Конституцией.

**4.1. Схема компонентов.**

```
              УГАР_Библиотека/ (MD, git) ←──────────────┐
                    │ exporter (валидация Д-1)          │ commit
                    ▼                                   │
              exports/*.json ──► compiler ──► окно N    │
                                     │                  │
                                     ▼                  │
                              writer-adapter (Gemini)   │
                                     │ текст N          │
                     ┌───────────────┴───────────┐      │
                     ▼                           ▼      │
                verifier-1 (скрипты)      verifier-2 (Claude)
                     │ verdict.json              │ flags.json
                     └───────────┬───────────────┘
                                 ▼
                        review (автор: правки, решения)
                                 │
                    edit-cycle: apply-edits → diff-check
                                 │ accept (автор)
                                 ▼
                          canonist (Claude) ──► пакет записей ──► подпись автора ─┘
                                 │
                     corpus/ + edits.jsonl + logs/ + dashboard
```

**4.2. Реестр модулей.**

| Модуль | Назначение | Вход | Выход | Интерфейс |
|---|---|---|---|---|
| `exporter` | MD → JSON-выгрузки, валидация структуры | библиотека | `exports/*.json` | `ugar export` |
| `compiler` | сборка окна главы | выгрузки, поглавник, № главы | `chapters/N/window.md` | `ugar compile N` |
| `writer-adapter` | вызов Gemini API | окно | `chapters/N/draft_k.md` | `ugar write N` |
| `verifier-1` | формальные проверки | текст, окно, корпус, выгрузки | `verdict.json` | `ugar verify1 N` |
| `verifier-2` | смысловые проверки (Claude) | текст, выгрузки, бриф | `flags.json` | `ugar verify2 N` |
| `review` | пакет приёмки автора | текст+вердикты | `edits.md`, `resolutions.json` | `ugar review N` |
| `edit-cycle` | внесение правок Писателем, дифф-контроль | правки, текст | `draft_k+1.md`, `diff_report.json` | `ugar apply-edits N`, `ugar diff-check N` |
| `canonist` | пакет записей в реестры и правил вкуса | принятый текст, правки, самоволки | `canon_batch.md` на подпись | `ugar canonize N` |
| `regression` | золотые тесты | корпус тестов | отчёт поймано/пропущено | `ugar regress` |
| `dashboard` | метрики по главам/части | логи, корпус | `dashboard.html` | `ugar dashboard` |
| `config/log` | конфиг, ключи, журнал API | — | `logs/api.jsonl` | сквозной |

## 5. Модель данных

**5.1. Канон.** MD-файлы в git; структура — по текущим соглашениям библиотеки (Д-1). Приёмка главы = один атомарный коммит: текст главы в `Проза/`, обновлённые реестры, обновлённые выгрузки, запись метрик.

**5.2. Выгрузки (`exports/`).** Генерируются только `exporter`-ом; правка руками запрещена (перетираются).
- `stoplists.json`: `{scope: "0.3"|"0.4", rule_id, items[], applies_to: {focal?|year?|all}, action: "запрет"|"флаг"}` — из 03/04 и Р-016 (усилители).
- `matrix.json`: `[{fact_id, fact, subject, from_chapter, source, note}]` — из 31; `from_chapter: null` = не знает.
- `plants.json` (закладки): `[{plant_id, what, placed: {vol,ch}, fires: [{vol,ch?}], status}]` — из 3.2/реестра тома.
- `norms.json`: числовые пороги Э1 — из 02 §5 (единственный источник порогов; в коде констант нет).
- `continuity.json` — из 33; `briefs.json` — из 23 (глава: дата, фокал, сцены, биты, запреты, объём).
- `corpus/` — принятые главы в нормализованном виде (для n-грамм и TTR-агрегата).

**5.3. Правки автора.** `edits.jsonl`: `{chapter, seq, before, after, class: "вкус"|"факт"|"канон"|null, note}`; класс проставляет Канонист, подтверждает автор.

**5.4. Конечный автомат главы.** Состояния: `собрано → сгенерировано → верифицировано-1 → верифицировано-2 → на-приёмке → правки → дифф-контроль → принято → зафиксировано`. Переходы: `верифицировано-1` при браке метрик → `сгенерировано` (авто, ≤2 повторов, затем стоп с вердиктом автору); `дифф-контроль` при самовольных изменениях → `правки`; `rollback` — в любое предыдущее состояние; `зафиксировано` — терминальное, изменения только через git-revert. Состояние хранится в `chapters/N/status.yaml` (Д-5).

## 6. Интеграции

**6.1. Писатель — Gemini API.** Модель и версия — пин в `config.yaml` (текущая: Gemini 3.1 Pro, Р-016); параметры генерации фиксированы конфигом (Д-6); один вызов = одна глава/сцена; system-инструкций вне окна нет — окно самодостаточно.

**6.2. Верификатор-2 / Канонист — Anthropic API.** Модель Sonnet-класса, пин в конфиге (Д-11); промпт-шаблоны — в `templates/`, версионируются git.

**6.3. Общие требования.** Ключи — только `.env`/переменные окружения, в `.gitignore` (Д-9); ретраи: 3 попытки с экспоненциальной паузой на сетевых/5xx; таймаут вызова 120 с; при исчерпании — понятная ошибка и подсказка ручного режима (NFR-3). Каждый вызов — строка `logs/api.jsonl`: `{ts, role, model, version, tokens_in, tokens_out, cost_est, chapter, duration}`. Приватность: только API-каналы с политикой необучения на пользовательских данных; передача текстов третьим сервисам (кроме двух API) запрещена.

## 7. Функциональные требования

### 7.1. Exporter
- **FR-X1.** Команда `export` перегенерирует все выгрузки из MD; расхождение структуры MD с соглашениями Д-1 → ошибка с указанием файла/строки.
- **FR-X2.** Выгрузки валидируются pydantic-схемами; невалидная выгрузка не записывается.
- **FR-X3.** `export` идемпотентен; хэши выгрузок пишутся в лог для контроля дрейфа канона.

### 7.2. Компилятор
- **FR-C1.** `compile N` собирает окно строго по шаблону v1.1 (`ПРОМПТ_Глава5.md`): разделы «роль и запреты», «регистр и стиль» (из 02 §1–4, 6.1 + пороги из `norms.json`), «фокализация» (общие законы 03 + правила линий только участников сцены), «персонажи сцены» (из досье: профиль 2–3 строки, физика, речевой паспорт, отношения к участникам), «что знает фокал» (из `matrix.json`: факты с `from_chapter ≤ N` для фокала + явные «НЕ знает» из брифа), «бриф» (из `briefs.json`: биты, запреты, объём), «формат выдачи».
- **FR-C2.** В окно включаются только закладки, назначенные главе N (`plants.json`), в секции техзадания, отделённой от знания фокала.
- **FR-C3.** Запрещено включать: полные файлы канона; факты матрицы, недоступные фокалу; резервы будущих томов (запреты информрежима из 2.2 включаются как явные «НЕ упоминать»).
- **FR-C4.** Детерминированность: одинаковые вход и выгрузки → байт-в-байт одинаковое окно.
- **FR-C5.** Оценка размера окна; при превышении лимита (Д-12) — флаг автору с раскладкой по секциям.
- **FR-C6.** Блок «СТРОГО ЗАПРЕЩЕНО» v1.1 (перенос формулировок промпта, досочинение мотивировок, усилители) включается всегда.

### 7.3. Writer-adapter
- **FR-W1.** `write N` отправляет окно, сохраняет ответ как `draft_k.md` с метаданными вызова; никакого контекста, кроме окна.
- **FR-W2.** Режим правок: вход = принятый черновик + список правок + инструкция «внести точно, не меняя ничего сверх» (шаблон в `templates/`).

### 7.4. Верификатор-1 (пороги — только из `norms.json`)
- **FR-V1.1.** Разбиение на предложения и слова по правилам Д-2; документы-вставки, размеченные маркером, исключаются из метрик повествователя (Д-7).
- **FR-V1.2.** Метрики: средняя длина фразы (норма 9–12; <7 — брак), доля ≤6 слов (30–45%), доля ≥25 слов (≤5%), максимум; объём против брифа.
- **FR-V1.3.** Плотность «был/было/были» ≤1/250 слов.
- **FR-V1.4.** Наречия-усилители по словарю ≤2/1000 слов.
- **FR-V1.5.** Запрещённая лексика: прогон по `stoplists.json` с учётом года главы и фокала (стоп-листы линий 0.3 — по фокалу).
- **FR-V1.6.** Вставка окна: поиск в тексте последовательностей ≥6 слов, дословно совпадающих с окном, — флаг «утечка промпта».
- **FR-V1.7.** Межглавные повторы: нормализованные n-граммы ≥5 слов против `corpus/` — флаг с указанием главы-источника.
- **FR-V1.8.** TTR: по главе — справочно; нарастающим окном 10 тыс. слов по части — контроль порога 0,46 (Д-3).
- **FR-V1.9.** Вердикт `verdict.json`: по каждой проверке `{check_id, status: PASS|FLAG|BRAK, threshold, actual, quotes[], rule_source}`; BRAK по FR-V1.2 запускает авто-повтор генерации (§5.4).
- **FR-V1.10.** Дифф-контроль (`diff-check N`): сопоставление черновиков до/после правок; отчёт: доля внесённых правок, список невнесённых, список самовольных изменений вне правок.

### 7.5. Верификатор-2
- **FR-V2.1.** `verify2 N`: вход — текст + релевантные срезы выгрузок (строки матрицы участников, бриф, закладки главы, запреты информрежима) + шаблоны чек-листов 4.1–4.3.
- **FR-V2.2.** Выход `flags.json`: `{type, severity, quote, rule, recommendation, kind: violation|samovolka}`.
- **FR-V2.3.** Обязательные проверки: фокализация (одна голова, стоп-листы линии, чтение чужих мыслей); эпистемика (использование знания с `from_chapter > N` или отсутствующего); информрежим (утечка тайн, резервы будущих томов); закладки главы положены/не положены; сверка фактов с брифом — все добавки → `samovolka`.
- **FR-V2.4.** Верификатор-2 не переписывает текст (Конституция §5): только флаги с цитатами.
- **FR-V2.5.** Самоволки собираются отдельным списком с обязательным полем решения автора: `resolutions.json: {flag_id, decision: "вычеркнуть"|"канонизировать", target_registry?}`.

### 7.6. Review и цикл правок
- **FR-E1.** `review N` формирует пакет приёмки: текст с якорями флагов Э1/Э2 на полях (MD с цитатами) + форма правок + форма решений по самоволкам.
- **FR-E2.** Правки автора принимаются файлом `edits.md` (пары «было → стало» и/или свободные указания) и конвертируются в `edits.jsonl`.
- **FR-E3.** `apply-edits N` — вызов Писателя в режиме правок (FR-W2); `diff-check N` — FR-V1.10; при самовольных изменениях цикл повторяется (≤3 итераций, затем ручная правка автора).
- **FR-E4.** `accept N` доступен только из состояния `дифф-контроль: чисто` и требует явного подтверждения.

### 7.7. Канонист
- **FR-K1.** `canonize N` формирует пакет `canon_batch.md`: новые факты (→ 3.1/3.2/3.3/1.2, с готовыми формулировками строк), канонизированные самоволки (по `resolutions.json`), кандидаты в правила вкуса из повторяющихся правок (→ 02 §6.1/6.2), обновление статуса главы и корпуса.
- **FR-K2.** Пакет применяется только после подтверждения автора; применение = правки MD + `export` + git-коммит с шаблонным сообщением (глава, Р-ссылки, счётчики).
- **FR-K3.** Ни один компонент, кроме `canonize` после подтверждения, не пишет в `УГАР_Библиотека/` (проверка в коде: путь записи).
- **FR-K4.** Отклонённые предложения Канониста логируются (для настройки его шаблонов).

### 7.8. Регрессия
- **FR-R1.** Золотой тест: `{test_id, fragment, context_slice, expected_flags[]}`; корпус пополняется командой из любой ошибки, пропущенной эшелонами и пойманной автором.
- **FR-R2.** `regress` прогоняет Э1 (всегда) и Э2 (по флагу `--llm`) по корпусу; отчёт «поймано/пропущено/лишние».
- **FR-R3.** Пропуск любого ожидаемого флага блокирует смену конфигурации (версий моделей, шаблонов промптов, порогов) — предупреждение при `accept` и запрет при `retest`-фиксации.
- **FR-R4.** Стартовый корпус — «красные» тексты отборочного теста с их известными нарушениями (раздел 10).

### 7.9. Дашборд и статус
- **FR-D1.** `dashboard` строит HTML: правки/1000 слов по главам; метрики Э1 по главам с коридорами и флагом отклонения >20% от среднего части; TTR нарастающим окном; расход токенов и стоимость по ролям.
- **FR-D2.** `status` — таблица глав и состояний FSM в терминале.

### 7.10. Оркестрация
- **FR-O1.** Этап 2: `run N` исполняет такт целиком с паузами на шагах автора (review, accept, canonize).
- **FR-O2.** Каждый шаг исполним отдельной командой (деградация в ручной режим, NFR-3).

## 8. Нефункциональные требования

- **NFR-1.** Локальный запуск: macOS и Windows; установка — `pip install` + `config.yaml` + `.env`; без Docker и серверов.
- **NFR-2.** Язык интерфейса, сообщений, отчётов — русский.
- **NFR-3.** Деградация: отказ любого компонента не блокирует такт — каждый артефакт (окно, вердикты, пакеты) — человекочитаемый файл, пригодный для ручного продолжения (копировать окно в чат модели руками).
- **NFR-4.** Все артефакты такта хранятся в `chapters/N/` и не удаляются (полная воспроизводимость истории главы).
- **NFR-5.** Журналирование каждого API-вызова (§6.3); журнал вне git (локально, в бэкап входит).
- **NFR-6.** Бэкап: репозиторий — минимум два удалённых/внешних места; команда `backup` — напоминание/проверка свежести.
- **NFR-7.** Производительность: полный машинный проход такта (без шагов автора) ≤5 минут; Э1 ≤5 секунд.
- **NFR-8.** Кодировка UTF-8 всюду; имена файлов — как в библиотеке (кириллица допустима).

## 9. Этапность

**Этап 1 «Скрипты» (оценка: 30–50 ч).** Состав: репозиторий и структура папок; `exporter` с валидацией; `compiler`; `verifier-1` полностью; адаптеры API с логом; команды `export/compile/write/verify1/status`. Критерии приёмки: окно главы 5, собранное `compile`, семантически эквивалентно эталону v1.1; счётчики на калибровочных текстах дают эталонные значения (раздел 10); сквозной полуручной такт главы выполнен.
**Этап 2 «Пайплайн» (40–60 ч).** Состав: FSM и `run`; `verify2`; цикл правок с дифф-контролем; `canonist`; регрессия; дашборд; `rollback`. Критерии: такт главы ≤40 минут работы автора; регрессия зелёная на стартовом корпусе; приёмка порождает корректный атомарный коммит.
**Этап 3 «Панель» (по желанию, 60+ ч).** React-интерфейс поверх пайплайна: очередь, чтение с флагами, инлайн-правки, кнопки решений, дифф, дашборд, журнал. Критерий: полный такт без терминала.

## 11. Риски и открытые вопросы

- **R-1.** Смена/деградация версии Писателя → дрейф голоса. Митигация: пин версий, пере-тест раз в том (Р-016), дашборд дрейфа.
- **R-2.** Региональная доступность API (география автора). Митигация: NFR-3 — ручной режим с любым доступным интерфейсом моделей; смена провайдера = пере-тест.
- **R-3.** Рост окна контекста с ростом библиотеки. Митигация: FR-C5 + выжимки вместо полных файлов; резерв — снапшоты.
- **R-4.** Ломкость парсера MD при правках структуры канона. Митигация: FR-X1 валидация + соглашения Д-1 как документ.
- **R-5.** Конфликт параллельных правок канона (автор правит MD во время такта). Митигация: `export` перед `compile` обязателен; хэш-контроль выгрузок.
- **R-6.** Открытый вопрос: точный ID и параметры моделей на момент старта разработки — вписать в `config.yaml` при настройке (Д-6, Д-11).

## 12. Критерии приёмки системы

1. Сквозной такт главы — ≤40 минут работы автора (замер по 10.4).
2. Все проверки Р-016 (а–д) автоматизированы и покрыты тестами.
3. Ни один путь записи в `УГАР_Библиотека/` не обходит подтверждение автора (FR-K3, код-ревью + тест).
4. Регрессия: 100% стартового корпуса ловится.
5. Отказ любого внешнего API оставляет возможность завершить такт вручную по артефактам системы.
6. Пороги и правила берутся только из канона/выгрузок; в коде нет «зашитых» норм.

## 13. Допущения (на утверждение автора, пакетом)

- **Д-1.** Соглашения структуры MD фиксируются документом `ИНСТРУМЕНТ_Соглашения_разметки.md` (создаётся на этапе 1 по фактической структуре библиотеки: таблицы реестров, маркеры ⚠/✓/🔧, маркер документов-вставок в прозе `→ ДОКУМЕНТ`). Канон не переформатируется под парсер — парсер пишется под канон.

- **Д-3.** TTR считается по словоформам без лемматизации (пороги калиброваны так же в замерах библиотеки).
