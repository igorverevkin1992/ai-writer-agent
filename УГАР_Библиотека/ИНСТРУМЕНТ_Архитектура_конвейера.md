# АРХИТЕКТУРА СИСТЕМЫ «КОНВЕЙЕР УГАР»
## Проектный документ программы для написания серии. Версия 1.0

Цель: максимально эффективная и качественная система производства прозы с контролируемой ошибкой. Честная рамка: «безошибочных» генеративных систем не существует; существует система, в которой (1) каждый класс ошибок ловится своим эшелоном ДО читателя, (2) каждая ошибка, дошедшая до автора, превращается в правило и больше не повторяется классом (регрессионный принцип), (3) единственный источник каноничности — автор.

---

## 1. Пять принципов проектирования

**П-А. Каскад защит.** Ошибка дешевле всего до генерации (канон и сборка контекста), дороже всего после приёмки. Система строится как последовательность фильтров, каждый ловит свой класс.

**П-Б. Детерминированное — коду, творческое — Писателю, вкусовое — автору.** Сборка промпта, счётчики, поиск повторов — код (не ошибается и не устаёт). Проза — LLM. Канонические решения и вкус — только человек.

**П-В. Разделение ролей по моделям (Р-016).** Писатель ≠ Верификатор ≠ Канонист: генератор не проверяет сам себя (Конституция §5); разные модели не наследуют слепые пятна друг друга.

**П-Г. Чистое окно.** Писатель не имеет памяти между главами: каждая глава генерируется из свежесобранного окна контекста (канон + снапшот + бриф). Это защита от дрейфа и от накопления самовольного канона.

**П-Д. Правки автора — топливо.** Каждая правка классифицируется и возвращается в систему: вкусовая → правило регламента 6.1/6.2; фактовая → реестр; каноническая → журнал 3.6. Система, в которой правки не капитализируются, не учится.

## 2. Роли (исполнители)

| Роль | Исполнитель | Функция |
|---|---|---|
| Шоураннер | Автор | Канонические решения, приёмка, вкус. Единственный источник истины |
| Компилятор | Детерминированный код | Сборка окна контекста главы из библиотеки. НЕ LLM |
| Писатель | Gemini 3.1 Pro (версия запиннена, Р-016) | Генерация прозы по окну. Больше ничего |
| Верификатор-1 | Скрипты (Python) | Мгновенные формальные проверки |
| Верификатор-2 | Claude | Смысловые проверки по чек-листам 4.1–4.3 |
| Канонист | Claude + подтверждение автора | Фиксация принятого в реестры, снапшоты |

## 3. Хранилище канона

- Вся библиотека — Markdown-файлы в **git-репозитории**: версии, история, откаты, diff любого изменения канона. Каждая приёмка = коммит.
- Машиночитаемые выгрузки для скриптов (генерируются из MD автоматически): стоп-листы (0.3, 0.4) → JSON; эпистемическая матрица (3.1) → таблица «персонаж × факт × глава»; закладки (3.2) → список с привязкой к главам; корпус принятых глав → для межглавных проверок.
- Правило Конституции §3 автоматизируется: приёмка главы без коммита фактов в реестры технически невозможна (один пайплайн).

## 4. Такт конвейера (жизненный цикл главы)

```
 [1] КОМПИЛЯТОР: собрал окно главы N ──────────────┐
      регламенты 0.1–0.4 (выжимки) + бриф сцены     │ код, 0 сек
      + строки матрицы участников + карточки        │
      + континуити локации/предметов + закладки N   │
      + эталоны 6.3 + запреты информрежима          │
 [2] ПИСАТЕЛЬ: сгенерировал текст ──────────────────┤ API, ~1 мин
 [3] ВЕРИФИКАТОР-1 (скрипты): формальный прогон ────┤ 0 сек
      brak? → автоправка компилятором брифа и шаг 2 │ (до 2 повторов)
 [4] ВЕРИФИКАТОР-2 (LLM): смысловой прогон ─────────┤ ~1 мин
      вердикт: ПРОШЛО/ФЛАГИ с цитатами              │
 [5] АВТОР: чтение с флагами на полях ──────────────┤ 15–30 мин
      правки; решения по флагам «самоволок»:        │
      вычеркнуть / канонизировать                   │
 [6] ПИСАТЕЛЬ: внёс правки точечно ─────────────────┤ «не трогая соседнего»
 [7] ВЕРИФИКАТОР-1: диф-контроль правок ────────────┤ внесено точно? самоволок нет?
 [8] АВТОР: финальная приёмка ──────────────────────┤ 5 мин
 [9] КАНОНИСТ: фиксация ────────────────────────────┘
      новые факты → 3.1/3.2/3.3/1.2; глава → корпус;
      правки → правила 6.1/6.2 (пакетом на подпись);
      git-коммит; счётчик части обновлён
```

Оценка такта: 20–40 минут работы автора на главу. Часть I (9 глав) — 2–4 сессии. Том — 2–3 месяца спокойного темпа.

## 5. Эшелоны верификации × классы ошибок

| Класс ошибки | Ловец | Механизм |
|---|---|---|
| Метрики фразы (телеграф/периоды, «был», объём) | Э1 скрипт | счётчики 0.2 |
| Запрещённая лексика, анахронизмы словарные | Э1 скрипт | стоп-листы 0.4 (JSON) |
| Вставка текста промпта в прозу | Э1 скрипт | substring-поиск по окну |
| Межглавный повтор фирменных фраз | Э1 скрипт | n-граммы 5+ слов против корпуса принятых |
| Наречия-усилители, клише-физиология | Э1 скрипт | словарь-счётчик (>2/1000 слов — флаг) |
| Нарушение фокализации, чтение чужих мыслей | Э2 LLM | чек-лист 4.1 п.2–3 |
| Использование знания, которого нет у фокала | Э2 LLM | сверка с матрицей 3.1 (JSON) |
| Утечка тайны читателю раньше срока | Э2 LLM | сверка с 2.2 + тест «глазами решившего слой 1» |
| Самовольные факты и мотивировки | Э2 LLM | сверка с брифом; список добавок на решение автора |
| Пропущенная закладка главы | Э2 LLM | сверка с 3.2 |
| Канон-конфликт (противоречие реестрам) | Э2 LLM + компилятор | компилятор кладёт релевантные факты в окно; Э2 сверяет |
| Дрейф стиля между главами | Э1 дашборд | графики метрик по главам; отклонение >20% от среднего части — флаг |
| Смысловой анахронизм (реалия, процедура) | Э2 + автор | хроника 1.7 (✓-факты) + флаг на ⚠ |
| Вкусовой брак | Автор | правки → правила (П-Д) |

**Регрессионный набор:** каждая ошибка, пойманная автором (пропущенная эшелонами), оформляется «золотым тестом» — фрагмент с этой ошибкой добавляется в тестовый корпус Верификатора; перед каждым томом Верификатор прогоняется по корпусу (должен ловить 100% старых ошибок). Так система со временем закрывает классы, а не случаи.

## 6. Обучающийся контур вкуса

1. Правки автора хранятся структурировано: (текст-до, текст-после, глава, классификация).
2. Раз в часть Канонист предлагает экстракцию: повторяющиеся паттерны правок → кандидаты в правила 6.1 и пары 6.2. Автор утверждает пакетом.
3. Метрика здоровья системы: **правок вкуса на 1000 слов по главам** — главный график дашборда. Должен падать; рост = дрейф Писателя или устаревший регламент → пере-тест по протоколу отбора.
4. Эталоны 6.3 пополняются только из принятых глав.

## 7. Интерфейс шоураннера (этап 3)

Очередь глав со статусами (собрано → сгенерировано → верифицировано → на приёмке → принято); чтение с флагами Э1/Э2 на полях; правка инлайн; кнопки решений по самоволкам (вычеркнуть/канонизировать); дифф-просмотр внесения правок; дашборд метрик (дрейф, правки/1000, TTR части); журнал 3.6 с поиском; git-история канона.

## 8. Дорожная карта внедрения

**Этап 0 — уже работает (ручной конвейер).** Всё выше исполнялось вручную в сессиях: библиотека есть, промпт-окно есть (v1.1), счётчики есть, чек-листы есть, приёмка есть, роли распределены. Писать книгу можно прямо сейчас, не дожидаясь программы.

**Этап 1 — скрипты (1–2 недели вечерами).** Репозиторий; JSON-выгрузки; компилятор окна (шаблон + подстановки из файлов); пакет счётчиков Э1 одним скриптом; скрипт-обвязка API Писателя и Верификатора-2. Результат: такт главы почти без ручной сборки.

**Этап 2 — пайплайн (месяц).** Связка шагов 1–4 и 6–7, 9 в один прогон; хранение правок; регрессионный корпус; дашборд-страница.

**Этап 3 — интерфейс (по желанию).** React-панель шоураннера поверх пайплайна (твой опыт web-инструмента переиспользуется). Программа — удобство, не условие: качество обеспечивают канон и эшелоны, а они готовы.

## 9. Эксплуатационные правила

- Версии моделей пиннятся и пишутся в журнал; смена версии = мини-тест (раунд 1 протокола на одном брифе) до допуска в конвейер. Плановый пере-тест — раз в том.
- Рукопись и канон — только через API с политикой необучения; git-репозиторий — приватный, бэкап в двух местах.
- Стоимость такта пренебрежима (доли доллара за главу с верификацией); оптимизировать некуда и незачем.
- Любой сбой конвейера деградирует в ручной режим этапа 0 — система не имеет единой точки отказа.
